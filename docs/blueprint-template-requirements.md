# 蓝图模板需求规格

> 目的：明确「蓝图」模板**要实现的效果**，供校验当前配置是否满足需求。
> 当前状态：已写入 `%AppData%\mindfs\task_template.json`（全局模板，所有项目共用）。

## 一、核心需求（用户提出）

用户在会话里用自然语言提出一个功能需求后，希望：

1. **Agent 先出技术方案**，不要直接动手写代码
2. **用户审核方案**，认可后才开始实现 —— 这是关键的人工卡点
3. **按批准的方案实现**，实现过程自动跑，不需要用户逐步确认
4. **独立验收** —— 验收必须用干净视角，不能受实现过程的对话影响
5. **尽量减少人工介入** —— 理想状态只有「填需求」和「审方案」两个卡点

## 二、期望的执行流程

```
[0] 需求    user    ← 用户填需求：目标、范围、验收标准
    ↓ 用户点开始
[1] 方案    agent   ← 出方案（涉及文件/接口契约/风险/验收标准），只出方案不改代码
    ↓ 自动推进（无需用户点击）
[2] 审核    user    ← ★ 卡点：用户审阅方案，认可则推进，有异议则写明要求
    ↓ 用户点推进
[3] 实现    agent   ← 按批准方案实现 + 测试，产出改动清单与偏差说明
    ↓ 自动推进（无需用户点击）
[4] 验收    agent   ← ★ 独立验收：全新会话 + 同一工作区，独立验证
```

**人工介入点：仅 [0] 和 [2] 两处。**

## 三、当前配置

| # | 阶段 | role | agent | model | auto_advance | session_reuse_policy |
|---|---|---|---|---|---|---|
| 0 | 需求 | user | — | — | false | task_main |
| 1 | 方案 | agent | claude | fable | **true** | task_main |
| 2 | 审核 | user | — | — | false | task_main |
| 3 | 实现 | agent | claude | opus | **true** | task_main |
| 4 | 验收 | agent | claude | fable | false | **always_new** |

**模型选择理由**：`fable` 用于判断密集型（方案/验收）、`opus` 用于执行密集型（实现）。
当前两个别名都映射到同一个模型，将来可分别指向不同模型。
（用别名而非具体模型名，是为了换 provider 时模板不用改。）

## 四、逐项校验需求符合性

### ✅ 需求 1：Agent 先出方案
- 阶段 1 是 agent 阶段，prompt 明确要求「只输出方案，不要修改任何代码、不要创建分支、不要提交」
- **符合**

### ⚠️ 需求 2：用户审核方案 —— **存在疑点**
- 阶段 2 是 `role: user`，理论上会停在 `waiting_user` 等用户
- **疑点 A**：阶段 1 的 `auto_advance: true` 会让它自动推进到阶段 2。
  但阶段 2 是 user 阶段 —— 自动推进时 `advanceManagedStage` 里
  `if stage.Role == RoleUser { t.Status = StatusWaitingUser }`，
  所以应该会正确停下。**需要验证**：自动推进到 user 阶段是否真的会停。
- **疑点 B**：阶段 1 自动推进时，会把阶段 1 的 `Result`（方案文本）写入阶段 2 的 `Input`。
  用户在阶段 2 填写的内容会**覆盖**这个 Input 吗？如果覆盖，方案文本会丢失吗？
- **疑点 C**：阶段 2 的 `prompt_template`（"请审阅上方方案..."）会作为**预填文本**出现在输入框。
  它和自动带过来的方案文本是什么关系？会冲突吗？

### ✅ 需求 3：按批准方案实现
- 阶段 3 是 agent 阶段，prompt 里用 `{previous_input}` 引用上一阶段内容
- **但依赖疑点 B**：如果审核阶段用户填写的内容覆盖了 Input，
  那么 `{previous_input}` 拿到的可能是**用户的审核意见**而非方案全文
- **需要验证**：实现阶段到底拿到什么

### ✅ 需求 4：独立验收 —— **设计上满足，待验证**
- 阶段 4 用 `always_new`，会创建全新会话
- 工作区是共享的（同一任务的 worktree），所以验收能看到实现改的代码
- **符合**（依据：`appcontext.go` 的 resolve 逻辑 + `RuntimeRootPath` 取自 `task.WorktreePath`）

### ⚠️ 需求 5：仅两个人工介入点 —— **待验证**
- 依赖疑点 A（自动推进到 user 阶段是否真的停）
- **需要端到端实测**

## 五、需要调研回答的问题

以下问题**必须由源码或实测回答**，不能靠推理：

1. `auto_advance: true` 的 agent 阶段，自动推进到 `role: user` 阶段时，任务状态是 `waiting_user` 还是会被跳过？
2. 自动推进时 `advanceManagedStage` 把上一阶段 `Result` 写入下一阶段 `Input`。
   若下一阶段是 user 阶段且用户填写了内容，**是覆盖还是追加**？
3. `user` 阶段的 `prompt_template` 是「预填到输入框的文本」。当该阶段已有自动带入的 `Input`（方案文本）时，
   两者如何共存？用户看到的是什么？
4. 实现阶段的 `{previous_input}` 最终拿到的是：a) 方案全文 b) 用户的审核意见 c) 两者拼接 d) 其他？
5. `always_new` 策略下，验收阶段能否正常读取 `{previous_input}`（即实现的交付说明）？
6. 验收阶段同一 worktree 的假设是否成立 —— 任务的 worktree 在整个任务生命周期内保持不变吗？

## 六、已知的坑（已实测确认）

1. **worktree 不能跨任务共享**：`depends_on` 只传 `Result` 文本，不共享目录。
   所以「拆成两个任务做实现+验收」的方案**不可行**——验收任务看不到实现的代码改动。
   → 验收必须留在同一任务的阶段内（当前设计已如此）。
2. **`existing` 分支模式不能复用工作区**：git 禁止同一分支被两个 worktree 同时检出。
3. **模板修改只影响新建任务**：任务创建时固化模板快照，已建任务不受影响。
4. **`create_worktree` 是建任务时的参数**，不是模板字段 —— 模板无法规定是否开 worktree。
   由父会话在建任务时决定。
5. **CLI 调用姿势**：`mindfs <root> -addr 127.0.0.1:7766 -tls -<操作>`
   （root 必须第一个参数；服务开了 TLS；默认端口 7331 连不上）

## 七、当前未决

- **是否开 worktree 由父会话决定，不在本模板控制范围内**。
  若不开 worktree，任务在项目主目录执行，多任务并行时有冲突风险（系统会强制串行）。
- 上述第五节的问题若无源码确证，需**实测验证**（新建一个任务跑完整流程，逐步检查）。
