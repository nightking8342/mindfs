# 蓝图模板需求规格

> 目的：明确「蓝图」模板**要实现的效果**，供校验当前配置是否满足需求。
> 当前状态：已写入 `%AppData%\mindfs\task_template.json`（全局模板，所有项目共用）。
>
> **本文件结构**：§一～§三 是需求与当前设计；§四 是实测校验；§五 是历史问题清单（保留作背景，
> 其中多数已在 §七 的改造中解决）；§六～§八 是改造后的设计与验证结论。

## 一、核心需求（用户提出）

用户在会话里用自然语言提出一个功能需求后，希望：

1. **Agent 先出技术方案**，不要直接动手写代码
2. **用户审核方案**，认可后才开始实现 —— 这是关键的人工卡点
3. **按批准的方案实现**，实现过程自动跑，不需要用户逐步确认
4. **独立验收** —— 验收必须用干净视角，不能受实现过程的对话影响
5. **尽量减少人工介入** —— 理想状态只有「填需求」和「审方案」两个卡点

**追加需求（2026-09-30）**：方案必须能被反复协商修改，且协商后的**定稿**才是实现依据。

## 二、当前执行流程（4 阶段，2026-09-30 定稿）

```
[0] 需求    user    ← 用户填需求：目标、范围、验收标准
    ↓ 用户点开始（发布即自动推进）
[1] 方案    agent   ← 出方案 + 落成文档 + 派子代理自检 → 停下等人
    ↓ 用户 -to-task 反复协商（agent 重跑并覆写文档）；满意后点「下一阶段」
[2] 实现    agent   ← 独立会话，读方案文档实现 + 测试 → 自动推进
    ↓ 自动推进（无需用户点击）
[3] 验收    agent   ← ★ 独立验收：全新会话 + 同一工作区，独立验证
```

**人工介入点：仅 [0] 的「填需求」与 [1] 的「协商/推进」两处。**

### 与旧版（5 阶段）的关键差异

旧版在「方案」与「实现」之间有一个 `role: user` 的**审核阶段**。实测证明它有三个问题（详见 §五、§七），故**删除**：

| 旧审核阶段 | 为什么删除 |
|---|---|
| 审核意见会**整体覆盖**方案正文（同一 `input` 字段） | 实现阶段因此拿不到方案 |
| 是 `user` 角色 → `-to-task` 只延续对话，**不触发 agent 重跑** | 无法多轮协商 |
| 对组内任务无法 `-prev`/`-jump` 回退 | 方案不满意只能重来 |

新设计的做法：让**方案阶段自己停下**（`auto_advance: false`），用户直接在该阶段协商。停在 agent 阶段的 `-to-task` 会**真正重跑** agent。

## 三、当前配置

| # | 阶段 | role | agent | model | auto_advance | session_reuse_policy |
|---|---|---|---|---|---|---|
| 0 | 需求 | user | — | — | false | task_main |
| 1 | 方案 | agent | claude | fable | **false** | task_main |
| 2 | 实现 | agent | claude | opus | **true** | **always_new** |
| 3 | 验收 | agent | claude | fable | false | **always_new** |

**模型选择理由**：`fable` 用于判断密集型（方案/验收）、`opus` 用于执行密集型（实现）。
当前两个别名都映射到同一个模型，将来可分别指向不同模型。
（用别名而非具体模型名，是为了换 provider 时模板不用改。）

### 三个设计要点

**① 方案落成文档（关键）**

方案 agent 把方案写入 `.mindfs/tasks/plan-{task_number}.md`（`{task_number}` 由 `promptValues` 注入）。

理由：`{previous_input}` 这个占位符读的是**上一阶段的 `Input` 字段**，而人工推进（`moveTo`）**不搬运上一阶段的交付正文**（只有自动推进 `advanceManagedStage` 才搬运）。所以关掉 `auto_advance` 后，方案正文无法通过字段流向下游——**文件绕开了这个限制**。

附带好处：
- `.mindfs/` 已被 `.gitignore` 忽略（worktree 内同样生效），不污染仓库
- 同一任务各阶段共用 `RuntimeRootPath`（`task.WorktreePath`），文件对下游可见
- 文件是**幂等覆写**，不像 `result` 字段会被后续消息覆盖

**② 实现阶段读文档，不依赖 `{previous_input}`**

实现阶段提示词改为「先读取 `plan-{task_number}.md`」，`{previous_input}` 降级为「路径线索，不作为方案依据」。

**③ 方案阶段交付前自检（子代理评审）**

方案写入后，派**一个**子代理独立评审（只读、不改文件、只出报告），主 agent 做「采信判断」：
逐条**实际验证**子代理的意见，只采纳验证为真的，并记录未采纳意见及理由。
详见 §七。

## 四、逐项校验需求符合性

### ✅ 需求 1：Agent 先出方案
方案阶段提示词明确「只输出方案，不要修改业务代码、不要创建分支、不要提交」。**符合**

### ✅ 需求 2：用户审核方案 —— **改造后满足**
方案阶段 `auto_advance: false`，交付后停在 `waiting_user`；用户可 `-to-task` 反复要求调整
（agent 重跑并覆写方案文档），满意后 `-next` 推进。**符合**

### ✅ 需求 3：按批准的方案实现 —— **改造后满足**
实现阶段读 `plan-{task_number}.md` 取得方案。实测：即使实现阶段的 `{previous_input}` 渲染为空，
仍能拿到完整方案（因为它读文件）。**符合**

### ✅ 需求 4：独立验收 —— **满足，且证明了有效性**
验收阶段 `always_new`（全新会话）。实测验证有效：验收者用**突变测试**验证测试用例的鉴别力、
以 goroutine 并发验证纯函数性质，并抓出实现阶段的事实错误。**符合**

### ✅ 需求 5：仅两个人工介入点 —— **满足**
仅「填需求」与「方案协商/推进」两处。**符合**

## 五、历史问题清单（改造前实测，保留作背景）

> 以下问题在 5 阶段设计下实测确认；其中多数已在 §七 的改造中解决，保留原文以便追溯。

### ❌ 问题 A：审核意见整体覆盖方案正文

`POST /api/tasks/{id}/input` → `UpdateStageRunInput` → `UPDATE stage_runs SET input=?`，单字段整体替换。
实测：向审核阶段写入 276 字审核意见后，该阶段 `input` 由 **1810 → 276**，方案正文被抹掉。
导致实现阶段 `rendered_prompt` 的 `## 方案` 段落只有审核意见、**没有方案**。

**已解决**：删除了审核阶段；方案改存文档。

### ❌ 问题 B：审核阶段无法「打回重做」

- `-next` 只向前推进（`moveTo(target = CurrentStageIndex+1)`）
- `-to-task` 在 **user 阶段**不走 `executeManagedTurn`，落到「只延续对话、不批准、不重开、不推进阶段」分支
- `-prev` / `-jump` 对组内任务被 `ManagedAction` 的 default 分支拒绝

**已解决**：方案阶段改为 agent 阶段后，`-to-task` 会真正重跑 agent（实测确认）。

### ⚠️ 问题 C：审核阶段实为「搬运工」

`moveTo`（人工推进）不携带上一阶段交付正文，只有 `advanceManagedStage`（自动推进）才写 `Input: result`。
审核阶段的存在正是为了补这个缺口。实测铁证：方案 `result`(1810) **逐字节等于**审核 `input`(1810)。

**已解决**：文档取代了「搬运」这一职责。

## 六、需要调研回答的问题 —— **已实测解答（2026-09-30）**

> 取证来源：`.mindfs/tasks/task-kanban.db` 的 `stage_runs`（`input` / `result` / `rendered_prompt`）
> 与 `task_events` 事件流，逐条与源码对照。

**旧版（5 阶段）实测链路**：

| stage | 名称 | 角色 | 状态 | 会话 | input | result | prompt |
|---|---|---|---|---|---|---|---|
| 0 | 需求 | user | waiting_user | — | 290 | 0 | 0 |
| 1 | 方案 | agent | success | `...29378` | 0 | **1810** | 464 |
| 2 | 审核 | user | waiting_user | — | **276** | 0 | 0 |
| 3 | 实现 | agent | success | `...29378` | 0 | **2612** | 1042 |
| 4 | 验收 | agent | success | **`...db70b`** | 2612 | **2952** | 3317 |

1. **`auto_advance` 推进到 user 阶段会停**。`advanceManagedStage` 对 `RoleUser` 阶段设 `StatusWaitingUser`，实测确认。
2. **用户填写会覆盖、不是追加**。见 §五 问题 A。
3. **方案正文与模板文案不共存**。输入框预填的是当前阶段 `input`；`role:user` 阶段的 `prompt_template`
   **不参与输入框预填**，只对 agent 阶段渲染 prompt 有用。
4. **`{previous_input}` = 上一阶段的 `input` 字段当前内容**。
   实测：实现阶段 `## 方案` 段落 = 276 字审核意见，方案全文不在其中。
5. **`always_new` 能正常读取注入内容**。实测验收阶段 `input` = 2612（实现交付），
   `rendered_prompt` 同时含「原始需求」与「实现交付说明」。
6. **worktree 在任务生命周期内不变**。`RuntimeRootPath` 取自 `t.WorktreePath`
   （`orchestration_execution.go:322`），该字段任务创建时建立、之后不变。

**任务 #11（子代理自检）**：见下。

### 方案阶段子代理自检（新增能力）

**流程**：方案写入 → 派一个子代理独立评审 → 主 agent 逐条**实证验证**意见 → 采纳为真的、记录未采纳的 → 覆写方案。

**评审标准**（融合 Anthropic 官方 LLM-as-judge rubric、开源 plan-review rubric、Uniswap plan-reviewer 实践）：

三层结构：
1. **确定性门禁**（必须先跑命令取证，不凭印象）：引用路径存在 / 声称的符号存在 / 现状描述与代码一致 /
   无未填占位符 / 给出可执行验收命令。任一门禁 fail → 判「阻塞」，不进入第二层。
2. **维度评分**（0-3，不取平均）：目标 / 证据 / 决策与未知 / 范围 / 风险 / 可验证。
   **长度、标题数、步骤数永远不得分。**
3. **禁止越界**：只评审当前需求，不得提需求外建议（不补测试计划 / 成功标准 / 风险矩阵 / 工时估算）。

**关键设计：主 agent 做「采信判断」，不是子代理**

子代理是顾问，主 agent 是责任人。要求逐条**实际验证**（跑它说的命令 / 读它指的文件），
确认问题真实存在才采纳；验证不成立的在方案「自检记录」中写明理由。

**实测效果（任务 #11）**：子代理提出 4 条意见，主 agent 逐条实证后**全部采纳**，例如——
子代理指出方案「断言包测试全绿」不成立，主 agent 连跑 8 次 `go test`，**2 次 FAIL**，
查明是 Windows 下 SQLite 临时目录文件锁（AGENTS.md 记载的已知环境性失败），
据此把包级回归判据放宽为「最多 3 次重跑内 ok」并加负判据。
同时，主 agent **拒绝了子代理的一处误判**（把「自检记录」节的回填占位符当成阻塞），并说明了理由。

**代价**：方案阶段耗时由 4-5 分钟增至约 16 分钟，方案文件由 7-11KB 增至约 19KB。

**已知坑**：若在方案里预留 `（待评审后填写）` 之类占位符，会被评审者判为门禁 fail。
模板已修正：要求评审**完成后再追加** `## 自检记录` 节，且门禁表明确该节不计入占位符判定。

## 八、已知的坑（已实测确认）

1. **worktree 不能跨任务共享**：`depends_on` 只传 `Result` 文本，不共享目录。
   → 验收必须留在同一任务的阶段内（当前设计已如此）。
2. **`existing` 分支模式不能复用工作区**：git 禁止同一分支被两个 worktree 同时检出。
3. **模板修改只影响新建任务**：任务创建时固化模板快照，已建任务不受影响。
4. **`create_worktree` 是建任务时的参数**，不是模板字段 —— 模板无法规定是否开 worktree。
5. **CLI 调用姿势**：`mindfs -<操作> <root>`（flags 必须在 root 之前；
   root 必须是注册表 id 而非路径）。**`-addr` 与 `-tls` 均可省略**：
   - `-tls`：v0.5.4 起 `resolveClientTLS` 从 `local-cli-tokens.json` 的 `tls` 字段自动发现。
   - `-addr`：fork 的启动配置默认路径生效——`-config` 未显式传时回落到
     `%AppData%\mindfs\config.json`，其中的 `addr` 由 `applyStartupConfig` 填入。
   **前提是同机同用户**（服务端与 CLI 共用同一个 `MindFSConfigDir()`），且服务须用
   含上述改动的版本启动过一次以写入 `tls` 字段。跨机器或跨用户时仍需显式 `-addr`/`-tls`。
   实测见 `task-orchestration-internals.md` §F25 修订小节。
6. **停机时不会通知父会话**：`stage_done` + `auto_advance=true` 推进后任务为 `queued`，
   不满足通知条件（`t.Status == StatusWaitingUser`），父会话要等下一阶段结束才被唤醒。
7. **组内任务不能主动 `fail`**：`Fail` 对 `Task.GroupID != ""` 直接返回
   `report task problems with -from-task`。
8. **阶段内多次 `from-task completed:true` 会互相覆盖 `result`**：`finishManagedRun` 遍历该 run 的
   所有 `from-task` 事件，`message` 被**最后一次**覆盖。实测：方案 agent 误以为提交失败而重发 3 次，
   最终 `result` 只剩最后一条（162 字澄清），方案正文被冲掉。
   → 这也是「方案落文档」优于「依赖 `result`」的又一理由（文件是幂等覆写）。
9. **`-to-task` 的消息必须自包含**：messageTurn 会**整体替换** prompt（`prompt = taskMessagesPrompt(inbox)`），
   本轮不再注入阶段模板。既有会话历史仍完整可见（模板在历史里），但**本轮新增的要求只来自消息本身**。
10. **重跑会新建 stage_run**：同一阶段可有多条 run，`LatestStageRun` 按 `created_at DESC` 取最新。
